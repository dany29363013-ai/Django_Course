HTTP Request/Response Anatomy

HTTP (HyperText Transfer Protocol) is the language clients and servers use to talk to each other. It's text-based, human-readable (mostly), and brutally simple once you strip away the complexity.

The HTTP Request

Every HTTP request has four main parts:

Component What It Is Example
Method The action you want to perform GET, POST, PUT, DELETE
URL / Path The resource you're targeting /api/v1/loans/
Headers Metadata about the request Content-Type: application/json
Body Optional data you're sending {"amount": 50000, "term_months": 12}
💡 Key Idea: Methods Have Semantics

HTTP methods aren't just random verbs—they have specific meanings:

  • GET: Retrieve data (should not modify anything)
  • POST: Create new resource or trigger an action
  • PUT: Replace an entire resource
  • PATCH: Partially update a resource
  • DELETE: Remove a resource

Why this matters: If you use POST when you should use PUT, you break caching, you confuse other developers, and you violate REST principles. Django REST Framework enforces these semantics in its generic views.

Real Request Example

Here's what an actual HTTP request looks like when sent to create a loan:

POST /api/v1/loans/ HTTP/1.1
Host: fintech-api.example.com
Content-Type: application/json
Authorization: Bearer eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9...
Accept: application/json
User-Agent: Mozilla/5.0

{
    "borrower_id": 12345,
    "product_type": "personal",
    "amount": 500000,
    "term_months": 24,
    "purpose": "business_expansion"
}

Let's break this down:

  • POST /api/v1/loans/ HTTP/1.1 — The request line: method, path, protocol version
  • Host — Which server we're talking to (important for virtual hosting)
  • Content-Type — Tells the server "I'm sending JSON"
  • Authorization — JWT token proving who I am
  • Accept — "I want JSON back, please"
  • User-Agent — What client software I'm using
  • Blank line — Separates headers from body
  • Body — The actual loan data

The HTTP Response

The server responds with three main parts:

HTTP/1.1 201 Created
Date: Mon, 15 Jan 2024 14:32:10 GMT
Content-Type: application/json
Content-Length: 256
Location: /api/v1/loans/67890/
X-Request-ID: req_abc123xyz

{
    "id": 67890,
    "borrower_id": 12345,
    "status": "pending_approval",
    "amount": 500000,
    "created_at": "2024-01-15T14:32:10Z",
    "interest_rate": 0.18
}
⚙️ Under the Hood: Status Codes Matter

The status code (201 Created) tells the client what happened. Common codes you'll see in DRF:

  • 200 OK — Success (usually for GET/PATCH)
  • 201 Created — Resource created (POST)
  • 204 No Content — Success but no body (DELETE)
  • 400 Bad Request — Client sent invalid data
  • 401 Unauthorized — Not authenticated
  • 403 Forbidden — Authenticated but no permission
  • 404 Not Found — Resource doesn't exist
  • 429 Too Many Requests — Rate limited
  • 500 Internal Server Error — Server crashed (your bug)

DRF automatically returns the right status codes if you use its generic views correctly. But if you write custom views, you are responsible.

Query Strings vs Body

Sometimes data goes in the URL as a query string:

GET /api/v1/loans/?status=pending&amount_gte=100000&page=2

When to use query strings:

  • Filtering, searching, sorting, pagination
  • Data that doesn't change server state
  • Bookmarks and shareable URLs

When to use the body:

  • Creating or updating resources
  • Large amounts of data
  • Sensitive data (though still use HTTPS!)
❌ Common Mistake: PUT vs PATCH Confusion

I've seen senior devs do this. Don't be them.

PUT = Replace the entire resource. If you omit a field, it becomes null/default.

PATCH = Update only the fields you send.

Example: If a loan has {amount: 500k, status: "pending", rate: 0.18} and you send:

PATCH /api/v1/loans/67890/ {"status": "approved"}

Only status changes. With PUT, you'd need to send all three fields or risk losing data.

Client-Server Model & Stateless Protocols

The web runs on a client-server architecture:

Stateless Protocol Explained

HTTP is stateless, which means:

Each request is independent. The server doesn't remember previous requests unless you explicitly make it remember.
📺 Anime Analogy: Hunter x Hunter Nen Ability

Imagine every HTTP request is like Gon using Jajanken. Each time he fires it, he has to charge it from scratch. The attack doesn't "remember" the previous one.

If Gon wants to do a combo attack, he has to explicitly set it up each time. Similarly, if you want the server to "remember" a user across requests, you need sessions or tokens—which we'll cover in Phase 3.

Why stateless? Scalability. Any server can handle any request. You can add 100 servers behind a load balancer, and they all work identically because no server holds special "state" about a user.

But wait—if HTTP is stateless, how do logins work? How does the server know you're you on page 2? Answer: Cookies and Tokens. These are mechanisms to pass identity information with every request, making each request self-contained.

What REST Means (And What People Get Wrong)

REST stands for Representational State Transfer. It's an architectural style (not a protocol, not a standard) defined by Roy Fielding in his 2000 PhD thesis.

The 6 REST Constraints

For an API to be truly RESTful, it must follow these rules:

Constraint What It Means Why It Matters
Client-Server Separation of concerns: UI logic on client, data logic on server Independent evolution, scalability
Stateless Server stores no client context between requests Reliability, visibility, scalability
Cacheable Responses must define themselves as cacheable or not Performance, reduced server load
Uniform Interface Resources identified in URLs, manipulated via representations Simplicity, decoupling
Layered System Client can't tell if connected directly or through intermediaries Load balancing, security layers, proxies
Code on Demand Servers can send executable code (optional) Reduced client complexity (rarely used)
⚠️ What People Get Wrong About REST

Myth: "Any JSON API is RESTful."

Reality: Most "REST APIs" are just HTTP + JSON. True REST requires:

  • Resources identified by URLs (/loans/123, not /getLoan?id=123)
  • Standard HTTP methods (GET/POST/PUT/DELETE)
  • HATEOAS (Hypermedia as the Engine of Application State)—responses include links to related actions

Honest truth: Even DRF doesn't enforce HATEOAS by default. Most production APIs are "REST-like" (resource-oriented HTTP APIs). That's fine. Focus on good design, not religious purity.

Resource-Oriented Design

In REST, everything is a resource identified by a URL:

# Good RESTful design
GET    /api/v1/loans/           # List loans
POST   /api/v1/loans/           # Create loan
GET    /api/v1/loans/123/       # Get loan 123
PUT    /api/v1/loans/123/       # Replace loan 123
PATCH  /api/v1/loans/123/       # Update loan 123
DELETE /api/v1/loans/123/       # Delete loan 123

# Nested resources
GET    /api/v1/loans/123/repayments/     # List repayments for loan 123
POST   /api/v1/loans/123/repayments/     # Create repayment for loan 123

Bad (non-RESTful) design:

GET /api/v1/getLoans?user_id=123
POST /api/v1/createLoan
GET /api/v1/deleteLoan?id=123

See the problem? Verbs in URLs, inconsistent methods, no resource hierarchy. This is RPC over HTTP, not REST.

JSON, Serialization, and Why APIs Exist

What is JSON?

JSON (JavaScript Object Notation) is a text format for representing structured data. It's language-independent but uses JavaScript-like syntax.

{
    "id": 67890,
    "borrower": {
        "id": 12345,
        "email": "banana.man@example.ng",
        "verified": true
    },
    "amount": 500000,
    "currency": "NGN",
    "status": "pending_approval",
    "repayments": [
        {"due_date": "2024-02-15", "amount": 25000},
        {"due_date": "2024-03-15", "amount": 25000}
    ],
    "metadata": null
}

Serialization Explained

Serialization = Converting complex objects (like Django models) into a format that can be transmitted (JSON).

Deserialization = Converting received JSON back into complex objects.

⚙️ Under the Hood: Why Can't We Just Send Models?

Django model instances are Python objects with methods, database connections, and circular references. You can't just "send" them over HTTP.

Problem 1: HTTP only transmits text (bytes). Python objects aren't text.

Problem 2: Even if you pickle (serialize) the object, the receiving end needs the exact same Python classes. A mobile app written in Swift can't unpickle Python.

Solution: Convert to a universal format (JSON) that any language can parse. That's what DRF serializers do—they're translation layers between Python objects and JSON.

Simple Serialization Example

# Django model instance
loan = Loan.objects.get(id=67890)

# Manual serialization (DON'T do this in production)
import json
data = {
    "id": loan.id,
    "amount": str(loan.amount),  # Decimal → string
    "status": loan.status,
    "created_at": loan.created_at.isoformat()  # datetime → string
}
json_string = json.dumps(data)  # Python dict → JSON string

# Deserialization
received_json = '{"amount": "500000", "status": "approved"}'
data = json.loads(received_json)  # JSON string → Python dict

DRF automates this with Serializers (covered in Module 2.2), but you need to understand what's happening under the hood.

Why APIs Exist

An API (Application Programming Interface) is a contract between services. It says:

"If you send me data in this format, I promise to process it and respond in this format."

Real-world example: Your fintech app needs to verify a customer's bank account. You don't have direct database access to their bank. Instead:

  1. You send a POST request to the bank's API with account details
  2. The bank validates and responds with account holder name
  3. Your app displays the name for confirmation

Without APIs: Every integration would require custom database connections, shared credentials, and tight coupling. APIs enable loose coupling—services evolve independently.

What Happens From URL to Response

Let's trace a complete request. You type https://fintech-api.example.com/api/v1/loans/123/ into your browser (or Postman). Here's what happens:

Step-by-Step Breakdown

  1. DNS Resolution: Your computer asks a DNS server: "What IP address is fintech-api.example.com?" DNS responds: 104.26.10.123.
  2. TCP Connection: Your browser establishes a TCP connection to that IP (three-way handshake: SYN, SYN-ACK, ACK). If HTTPS, TLS negotiation happens here.
  3. HTTP Request Sent: Your browser sends the HTTP request we saw earlier.
  4. Load Balancer: Receives the request, checks SSL termination, applies rate limiting, and forwards to an available Django server (round-robin or least-connections).
  5. Django Request Processing:
    • WSGI/ASGI handler receives the request
    • Middleware stack processes it (authentication, CORS, sessions)
    • URL resolver matches /api/v1/loans/123/ to a view function
    • View executes: queries database, runs business logic
    • ORM generates SQL: SELECT * FROM loans WHERE id = 123;
  6. Database Query: PostgreSQL executes the query and returns the row(s).
  7. Serialization: Django converts the model instance to JSON via DRF serializers.
  8. Response Built: Django wraps JSON in an HttpResponse with status code and headers.
  9. Response Travels Back: Through middleware (again), through load balancer, over TCP, to your browser.
  10. Browser Renders: Your browser (or API client) parses the JSON and updates the UI.
💡 Key Idea: Middleware Runs Twice

Middleware processes requests before they reach the view, and responses after the view returns. Think of it as a layered onion:

Request:  Middleware 1 → Middleware 2 → View
Response: View → Middleware 2 → Middleware 1 → Client

This is crucial for things like authentication (check on request in) and logging (log on response out).

Total time: For a simple API call, this entire journey might take 50-200ms. Most of that is network latency, not Django processing.

✅ Exercise Solutions

Solution 1: HTTP Method Matching

1-GET (retrieve list, read-only)
2-POST (create new resource)
3-PATCH (partial update)
4-PUT (full replacement)
5-DELETE (remove resource)

Why: Each method has semantic meaning. Using them correctly enables caching, makes APIs predictable, and follows REST conventions that DRF expects.

Solution 2: Status Code Detective

1. 201 Created (resource successfully created)
2. 403 Forbidden (authenticated but no permission - different from 401!)
3. 400 Bad Request (validation error, client's fault)
4. 404 Not Found (resource doesn't exist)
5. 429 Too Many Requests (rate limiting)

Key distinction: 401 = "I don't know who you are." 403 = "I know who you are, but you can't do this." DRF handles these differently.

Solution 3: RESTful URL Design

1. GET  /api/v1/shops/456/products/
2. POST /api/v1/shops/456/sales/
3. GET  /api/v1/shops/456/sales/789/
4. PATCH /api/v1/shops/456/products/123/
5. DELETE /api/v1/shops/456/products/999/

Note: Shop ID is part of the URL hierarchy (nested resource). This enforces multi-tenancy at the URL level—you can't accidentally access another shop's data.

Solution 4: Loan Repayment Trace

1. Browser resolves DNS: fintech-api.example.com → 104.26.10.123
2. TCP three-way handshake with server
3. TLS negotiation (HTTPS encryption)
4. Browser sends HTTP POST request with JSON body
5. Load balancer receives request, terminates TLS
6. Load balancer checks rate limit (Redis/Upstash)
7. Load balancer forwards to Django server #3 (least loaded)
8. Django WSGI handler receives request
9. SecurityMiddleware checks HTTPS, CSRF (if applicable)
10. CorsMiddleware adds CORS headers
11. AuthenticationMiddleware parses JWT from Authorization header
12. URLResolver matches /api/v1/loans/12345/repayments/ to RepaymentViewSet.create()
13. View checks permissions (IsAuthenticated, IsOwner)
14. Serializer validates amount > 0, payment_method valid
15. View opens transaction.atomic() block

17. Business logic: calculate new balance, check for overdraft
18. ORM: INSERT INTO repayments (...) VALUES (...)
19. ORM: UPDATE loans SET balance = ... WHERE id = 12345
20. Transaction committed
21. Signal triggers: send_receipt_email() (background task)
22. Serializer converts repayment instance to JSON

Key learnings: Notice the database uses FOR UPDATE (row locking) to prevent race conditions. The email is sent asynchronously (doesn't block response). Middleware runs both directions.

Solution 7: Idempotent Payment Endpoint

# API Design
POST /api/v1/payments/
Headers:
  Idempotency-Key: <uuid-generated-by-client>
  Content-Type: application/json
  
Body:
{
    "loan_id": 12345,
    "amount": 25000,
    "currency": "NGN",
    "payment_method": "card",
    "card_token": "tok_visa_4242"
}

# Status Codes
- 201 Created: First successful request
- 200 OK: Duplicate request with same key + same data (return cached response)
- 409 Conflict: Same key but different data (potential fraud/bug)
- 410 Gone: Key expired after 24 hours (client should retry with new key)

# Database Schema
CREATE TABLE idempotency_keys (
    key VARCHAR(255) PRIMARY KEY,
    created_at TIMESTAMP DEFAULT NOW(),
    expires_at TIMESTAMP NOT NULL,
    request_hash CHAR(64) NOT NULL,  -- SHA256 of request body
    response_body JSONB NOT NULL,    -- Cache the full response
    status_code INTEGER NOT NULL
);
CREATE INDEX idx_expires ON idempotency_keys(expires_at);

# Pseudocode
def create_payment(request):
    idempotency_key = request.headers.get('Idempotency-Key')
    if not idempotency_key:
        return 400, {"error": "Idempotency-Key header required"}
    
    request_hash = sha256(request.body)
    
    with transaction.atomic():
        # Try to get existing key (FOR UPDATE to prevent race)
        try:
            cached = IdempotencyKey.objects.select_for_update().get(key=idempotency_key)
            
            if cached.expires_at < now():
                return 410, {"error": "Idempotency key expired"}
            
            if cached.request_hash != request_hash:
                return 409, {"error": "Key reused with different data"}
            
            # Return cached response
            return cached.status_code, cached.response_body
            
        except IdempotencyKey.DoesNotExist:
            # First time seeing this key - process payment
            response_status, response_body = process_payment_logic(request)
            
            # Save for future duplicates
            IdempotencyKey.objects.create(
                key=idempotency_key,
                expires_at=now() + timedelta(hours=24),
                request_hash=request_hash,
                response_body=response_body,
                status_code=response_status
            )
            
            return response_status, response_body

Trade-offs discussed:

  • Header vs body: Header is better—can check idempotency before parsing body, works even if body parsing fails.
  • Row locking: SELECT FOR UPDATE prevents two simultaneous requests with same key from both inserting.
  • Hash comparison: Prevents malicious reuse with different amounts.
  • Expiration: Prevents table bloat; 24h is typical but depends on business needs.

Solution 8: Teach Statelessness (Sample)

Think of HTTP like a vending machine. Every time you press a button 
(request), the machine processes it fresh. It doesn't remember you 
bought a soda 5 minutes ago.

Why? Imagine 100 vending machines (servers) at a stadium. If each 
remembered different customers, you'd have to use the SAME machine 
every time. Statelessness means ANY machine can handle ANY request.

"But how do logins work?" Great question! We attach a "membership 
card" (session token/JWT) to EVERY request. Like showing your ID at 
each checkpoint in World Trigger. The server doesn't remember you—
you prove who you are every single time.

That's stateless: no memory between requests, but full context WITH 
each request.

Solution 9: REST vs RPC (Sample Code Review)

@teammate Nice thinking on separating these operations! However, I'd 
suggest we make these resource-oriented instead of action-oriented.

Current approach problems:
- Hard to cache (all POST requests bypass caches by default)
- Discoverability suffers (can't guess URLs)
- Mixes concerns (calculation vs resource representation)
- Breaks DRF's generic view patterns

RESTful alternatives:
- `/api/loans/{id}/` with `amount` and `term` → server calculates 
  interest automatically and returns it in the response
- `/api/verifications/sms/` POST to create a verification resource; 
  the act of creation triggers SMS sending

Exception where RPC-style is okay:
- Truly procedural operations with no clear resource model, like 
  `/api/admin/clear-cache/` or `/api/webhooks/test-delivery/`. But 
  even then, consider if it could be a resource (CacheClearRequest?).

Cheat Sheet: HTTP Status Codes

  • 200 = Success (GET/PATCH)
  • 201 = Created (POST)
  • 204 = No Content (DELETE)
  • 400 = Bad Request (validation)
  • 401 = Unauthorized (no login)
  • 403 = Forbidden (no permission)
  • 404 = Not Found
  • 429 = Rate Limited
  • 500 = Server Error
